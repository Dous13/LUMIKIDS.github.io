# Firebase security rollout

## Local verification

Put an up-to-date Node.js 22 release on `PATH` and confirm it with `node --version`. Run `npm ci` in the app directory and `npm --prefix backend/functions ci --engine-strict` for Functions. Keep `JAVA_HOME` set to a Firebase CLI-compatible JDK. The Functions deployment target is Node 22. The Functions manifest pins the Admin SDK's database compatibility dependency to a version that supports Node 22. The rules test library is pinned by the app lockfile.

- `npm run test:firebase` compiles the existing curriculum for Node, starts Auth, Firestore and Functions under `demo-lumikids`, and runs the real SDK authorization tests.
- `npm run test:regressions` runs the SQLite, offline, curriculum and worksheet tests.
- For a development app connected to the same emulators, use `EXPO_PUBLIC_FIREBASE_EMULATOR_HOST` with the host address reachable by the device. The app uses project `demo-lumikids` in this mode. The checked-in emulator listeners bind to loopback. A physical-device test needs local forwarding or an intentional test-only listener binding. Release builds ignore this development setting.

## Identity and writes

The student enters their registered name and classroom code. `loginStudent` checks the classroom, teacher, student record, roster and access grant. It returns the existing student ID and a Firebase custom token. The identity uses UID `student:<id>` and signed student, classroom and grant-version claims. Teacher email/password registration and classroom enrollment use restricted writes. A reserved student UID cannot use teacher privileges.

Login errors use the same message for unknown names, unknown classrooms and exhausted budgets. In each five-minute window the server counts up to 120 failed attempts per source, up to 12 failures for a name slot within that source, and up to 12 token issuances per source and enrolled student. Once a name slot is full, further attempts in that slot stop using the shared failure budget. A classroom has no shared budget. Students on one school network still share the source limit, and different names can share one of the 256 slots. Unknown classroom codes all charge the source's existing failure bucket. Set Firestore TTL on `loginLimits.expiresAt` to remove expired documents.

In the emulator, rate limiting uses the socket peer. The deployed callable uses only the last valid address at the end of `X-Forwarded-For`, assuming the managed ingress appends that address after any client-provided prefix. If the header is missing or its final address is invalid, it uses the socket peer. Before approval, verify that the staging route yields a stable address for each source and varying the client-supplied prefix has no effect. An extra proxy can cause multiple callers to share its address and budget. [Cloud Functions request headers](https://docs.cloud.google.com/functions/docs/reference/headers) · [Google Cloud load-balancer forwarding](https://docs.cloud.google.com/load-balancing/docs/https#x-forwarded-for_header)

Firestore grants students reads of their own root profile and worksheet history while their enrollment and grant remain valid. Teachers can read only their assigned classrooms, rosters and students. Cloud score, balance, receipt and worksheet writes go through authenticated callable Functions. The server checks Auth token revocation and enrollment, validates attempts against curriculum and tracing rules, derives outcomes and prices, and atomically mirrors progress to the root and roster. Student-operation receipts are private, match the exact operation on retry, and are committed with the corresponding progress. The assigned teacher submits worksheet review choices. The server validates worksheet identity, grades the choices, and commits the result and progress together. Photos remain on the device. Trace coordinates are carried in the local outbox and examined in the callable, then discarded on acknowledgement. The cloud receipt stores a digest.

## Offline behavior and existing records

Firebase Auth stays in memory for both roles. The saved offline session contains the student ID and expiry. A cold start can reopen saved learning and worksheets without granting cloud access. Use **Sign in to sync your saved progress** on Home to reauthenticate with the same name and code. Expired or revoked cloud credentials block uploads while preserving SQLite records and pending jobs. Logout clears the local session and signs out the student from Firebase.

SQLite adds an operation payload and rejection reason to the existing journal where needed, along with a blocked flag on queue jobs. The first successful reconciliation of an older wallet uses the confirmed server balance and avatar as the base and keeps legitimate pending purchases and equipment changes. Historical scores and XP without supporting attempts remain on the device. They need a trusted migration or a new validated attempt for cloud confirmation.

An invalid operation or conflicting receipt stays in SQLite with its rejection reason for inspection. The worker skips those rows and continues to later work. A temporary connection failure keeps the original operation and receipt ID available for retry. An operation waiting for funds, mascot ownership, or a lesson unlock remains eligible once its prerequisite reaches the server.

Offline worksheet dates are accepted. Creation, capture and finalization timestamps may be up to five minutes ahead of the server clock. The server retains the newer legitimate draft. If an older draft contains an implausibly future capture date, a legitimate replacement can supersede it. If an offline device clock was incorrect when the worksheet was created, correct the device clock and reissue the unsubmitted worksheet. Worksheets for levels unlocked offline may wait for that learning to sync before the teacher can publish the review.

The backend accepts verified root-only legacy students only when the record has a matching teacher and classroom. Its first confirmed update can create the missing roster mirror. Reconcile any older records without verifiable ownership through a trusted administrative process.

## Before any production cutover

1. Approve the deployment separately. Review the rules and Functions in a staging Firebase project with synthetic accounts. Use Node 22 for the staging Functions runtime. Enable Firestore, Firebase Auth with the existing teacher password provider, and Cloud Functions with the required billing plan.
2. Treat the prior open-rule data as untrusted. Use a clean project or first close anonymous writes and verify the data against a trusted backup or enrollment source. Verify teacher UIDs, class ownership, root and roster identities, legacy progress and balances. Keep trusted student IDs. Use empty or trusted `studentAccess`, `loginLimits`, and receipt collections.
3. Configure the Functions service identity with least-privilege Firestore access, Auth user/revocation reads, and permission to sign custom tokens through the IAM signing service. Use platform credentials. Choose the release sequence so the restrictive rules and Functions are in place when the replacement client goes live. Older unsigned builds cannot sync through those rules. Keep offline records available during an upgrade. [Firebase custom-token configuration](https://firebase.google.com/docs/auth/admin/create-custom-tokens)
4. For immediate student cloud revocation, disable the trusted `studentAccess/{id}` grant or increment its version. Revoke Auth refresh tokens as well. A disabled grant blocks fresh name/code login. Re-enabling the account with a newer version requires a new sign-in.

A registered name and shared classroom code can let someone who knows both impersonate the student. The custom token identifies the enrollment granted by the server. Bundled quiz answers and tracing templates can be extracted and used to fabricate attempts with a modified client. Server validation rejects arbitrary scores, XP and coin totals and enforces progression and reward limits. It cannot establish whether a child personally completed the activity.
